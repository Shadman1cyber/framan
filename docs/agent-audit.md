# FARMAN agent audit — Phase 0

Inspected 2026-09-09. Target: `docs/agent-execution-plan-fa.md`. No applicable AGENTS.md was found in this repository or its ancestor directories. README.md, package scripts, schema, middleware and deployment files were inspected. The working tree already contained extensive modified/untracked application work; it must not be reset. Environment values and database contents were not inspected.

## Actual architecture

- `package.json`: Next.js 14 App Router, React 18, TypeScript, Zod 3, NextAuth 4, Prisma 5; Vitest 2. No Python runtime, LangGraph, graph/vector client, OTel SDK or background worker dependency.
- `src/app/api/**/route.ts`: backend HTTP handlers in the same Next.js process. `src/components/admin/AiAdmin.tsx` and `src/app/admin/(panel)/ai/page.tsx`: Persian admin chatbot/accountant UI.
- `prisma/schema.prisma`, `src/lib/db.ts`: SQLite operational database and shared Prisma client. Existing models include User, Cafe, Branch, CafeTable, Order/OrderItem, Product and recipe/allergen joins, Ingredient, Staff, TableReservation, Setting, AIInsight, AIChatSession/AIChatMessage, ImportJob. No invoice, payment, ledger, task, permission-version, tenant-membership or execution models existed at audit time.
- `src/lib/auth.ts`: credential verification with bcrypt, JWT session carries user ID and role. `src/lib/constants.ts`: OWNER has all permissions, CASHIER a limited operational subset, CUSTOMER none of the management permissions; ADMIN/STAFF normalize to OWNER/CASHIER. `src/lib/guards.ts`/`src/lib/api.ts` rely on cached JWT role. Agent execution must instead reload the role from User at every action.
- `src/middleware.ts` protects admin pages, not agent APIs. API handlers need independent authentication and authorization. `src/lib/table-session.ts` signs guest table cookies; these are not agent credentials.
- Tenant isolation is **absent**: Cafe/Branch exist but User, Product, Setting, Staff and takeaway Order have no cafe ownership. An owner can currently access installation-wide data. Inventing a tenant predicate would give false assurance. Initial runtime is explicitly single-cafe per database, requires server-configured cafe ID and exactly one matching Cafe, and fails closed otherwise. Shared-database multi-tenant use requires a separate authorized membership/backfill design before enablement. Cross-user run access is denied.
- `src/lib/ai/provider.ts`: server-side Zhipu GLM chat completions with 30s timeout; interface only returns text and usage, no native function-call contract. `src/lib/ai/service.ts`: keyword topic routing, last six turns, analytical response. `src/lib/ai/context.ts`: broad database summaries without retrieval provenance/ACL metadata. `src/lib/ai/settings.ts`: real reversible `setAiEnabled` operation on Setting. This is the first write tool; order transitions were rejected because their workflow has no general reversal.
- `src/app/api/admin/ai/chat/route.ts` and `chats/**`: chat persistence originally lacks per-user ownership checks. The new execution path must not inherit this access pattern.
- `src/lib/analytics.ts`: SQL aggregates and JavaScript reporting, prices/totals are integer tomans (`src/lib/ai/context.ts`). Existing revenue statuses include unfinished orders; this is not payment settlement or accounting profit. New report explicitly counts COMPLETED orders over an explicit half-open UTC interval and labels tomans. Inventory costs/quantities are Float, unsuitable for a new exact financial ledger.
- `src/lib/orders.ts`: pricing and business transitions; `src/lib/cart.ts`: authoritative cart pricing; `src/lib/storage.ts`: local uploads abstraction; `src/lib/importer.ts`: imports. These are future integration surfaces, not automatically exposed tools.
- `vitest.config.ts`, `src/lib/**/*.test.ts`: node tests, mostly isolated/mocked. `scripts/e2e-tables.js` is an existing browser workflow. No CI workflow found. Existing tests are not proof of authenticated agent execution.
- `Dockerfile`, `docker-compose.yml`: Node 20 Alpine, persistent SQLite/uploads volumes, one Next server. `run.sh` can sync/seed the database; do not invoke it for agent validation against an unknown DB. No OpenObserve destination configured initially. No production commands run for this work.

## Integration decision

Keep SQLite and the TypeScript backend for the first bounded slice. Additive execution tables in the same database allow setting mutation, verification and durable receipt to commit atomically. Apply schema only to disposable development/test databases during this session. Supply up/down SQL for review; no primary database migration or provider conversion is authorized or needed.

LangGraph/Python plus PostgreSQL would add an authenticated internal API, two connection stacks and a distributed transaction boundary before the first tool works. A later Python supervisor can call these named authenticated tools using delegated, bounded capabilities; it must never receive a database/admin credential. PostgreSQL agent state and Neo4j remain target options for subsequent phases, with an outbox required across stores. They are not claimed implemented by a TypeScript state machine.

Model output is an untrusted strict JSON proposal using existing completion transport; the server resolves the actual tool, scope, permission, approval and result. No arbitrary SQL/shell, policy edits or skill activation. A structured UI path works without a model credential. Financial results are formatted from authoritative deterministic output, never a model-written success statement.

Telemetry targets OpenObserve's OTLP/HTTP endpoint (`https://openobserve.ai/docs/ingestion/traces/opentelemetry/`, checked 2026-09-09). Durable local events are authoritative; collector availability must not roll back a completed business operation. Full retrieval/model/cost telemetry belongs to later acceptance work.

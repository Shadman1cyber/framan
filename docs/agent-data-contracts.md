# Phase 1 data contracts

Canonical validators: `src/lib/agent/contracts.ts`. All HTTP mutation bodies are strict JSON, max 8192 bytes; same-origin header must match NEXTAUTH_URL. Identity comes from NextAuth session ID; role is reloaded from User. No request/model tenant, user ID, policy, role or approval grant fields are accepted.

POST `/api/admin/agent/runs`: `{key, question}` OR `{key, proposal:{tool,input}}`. Key is 8–100 ASCII letters/digits/underscore/hyphen. Question 2–1000 characters. Create returns `{run,answer}`. It never executes a write. GET collection returns last 30 caller-owned runs. GET `/runs/{id}` includes last 100 events.

Tools:

- `get_ai_status`, input `{}`: ai.use, read, 5s transaction timeout; output enabled, version, source, verified.
- `set_ai_enabled`, input `{enabled:boolean}`: ai.configure, reversible write, explicit exact approval plus AGENT_WRITES_ENABLED, 5s transaction timeout; output enabled, version, previous, source, verified. Uses existing `setAiEnabled` service inside the execution transaction. Reversal is a separately authorized new opposite-value request.
- `calculate_sales_report`, input `{from,to}`: finance.view, read, explicit ISO UTC timestamps, positive interval up to 31 days, 5s transaction timeout. Uses the SHARED reporting service (`src/lib/reporting.ts` `completedSalesSummary`) — the same object the finance pages render — so chat answers and the UI can never disagree. Output: total/count, byDay (daily totals), byProduct (top 10 line totals from OrderItems), byCategory, basis, sources, plus `text` (the honest Persian rendering used verbatim as the chat answer). It is completed order value, not cash receipts, expenses or profit. Unsafe integer sums are rejected (`UNSAFE_MONEY_VALUE`, terminal failed). The caller's transaction client is passed through, so reads stay on the same connection.
- `search_catalog`, input `{query: 2–200 chars}`: ai.use, read, 5s transaction timeout. Queries the derived knowledge graph over Category/Product/Ingredient/Allergen/DietaryTag with relations BELONGS_TO/CONTAINS/USES/TAGGED. Output: count, results (kind, refId, label, sourceId, sourceVersion, observedAt, relations with source IDs), graphAsOf, stale, synced, source=Graph:catalog, verified. Volatile numbers (prices, stock, money) are never served from the graph; the tool may write only derived Graph* tables during bounded sync, never business data. Deleted/expired nodes and edges never surface. No embeddings in the SQLite interim: exact/substring label matching, deliberately conservative; every result carries its source ID for live-source verification.

- `list_lessons`, input `{topic?: 2–60 chars}`: ai.use, read, 5s transaction timeout. Returns only active, valid (validFrom ≤ now < validTo) lessons with live-resolved evidence (runId, tool, state, lastError from AgentRun). Drafts, rejected, superseded and expired lessons never surface. Output: count, lessons (topic, statement, evidence, validFrom, validTo), source=AgentLesson, verified.

Admin-section read tools (R05 extension, all 5s transaction timeout, one shared `sectionRead` implementation for run path + skill sandbox, no secrets):

- `list_products`, input `{take?: 1–30}`: products.manage; output count, products (id, nameFa, price, isAvailable, categoryId), source=Product:live.
- `list_categories`, input `{}`: categories.manage; output count, categories (id, nameFa, isActive, productCount), source=Category:live.
- `list_tables`, input `{}`: tables.manage; output count, tables (id, number, label, isActive, isOccupied), source=CafeTable:live.
- `list_qr_codes`, input `{take?: 1–20}`: qr.manage; output count, qrCodes (id, code, label, isActive, expiresAt, tableId), source=QRCode:live.
- `list_users`, input `{take?: 1–20}`: users.manage; output count, users (id, name, email, role, createdAt); passwordHash and phone are never selected, source=User:live.
- `list_ratings`, input `{take?: 1–20}`: ratings.moderate; output count, ratings (id, rating, review, createdAt, productName), source=Rating:live.
- `list_allergens`, input `{}`: allergens.manage; output count, allergens (id, key, nameFa, nameEn), source=Allergen:live.

POST `/runs/{id}`: `{action,inputHash?,note?}`. Actions execute, approve, reject, pause, resume, cancel, correct. Approve requires exact 64-character hash; server also checks source version and expiry. Model proposal cannot supply the hash or transition state. Approvals belong to the same authenticated owner; this is explicit self-approval, not two-person review. `correct` records a bounded user correction note (2–500 chars, validated in both HTTP schema and runtime) on any non-running run and writes to its AgentEpisode.

## Phase 4 memory and lesson contracts

`AgentEpisode` (unique per scope+run): durable facts derived from real outcomes only — tool, terminal/attempt state, `errorCode` (bounded code, e.g. WRITES_DISABLED), and optional bounded user `note` (correction). Episodes are created automatically inside the outcome transactions (success, durable failure, attempt recording); never model-invented.

`AgentLesson`: `topic` (3–60), `statement` (5–500), `status` (draft|active|rejected|superseded), `evidence` (JSON array of run IDs, validated at proposal time: caller-owned, same scope, terminal **or** durably recorded error via `lastError`), `proposedBy`/`reviewedBy`, `validFrom`/`validTo`. Lifecycle: propose (ai.use, evidence checked) → activate (ai.configure, explicit human action — the model has no lesson capability) → same-topic activation supersedes the previous active lesson (status=superseded, validTo=now; conflict handling, never deleted) → expire (sets validTo) or reject (draft only). At most one active lesson per topic per scope.

Learning loop (Phase 4 acceptance): a real failed/corrected run → episode fact → human proposes lesson citing that run → explicit activation → `list_lessons` surfaces it with live evidence in the next response. Reflection never proposes lessons in this version; no weight updates; no skill self-activation; lessons are advisory text and carry no permissions.

## Phase 5 skill contracts

`AgentSkill` (unique per scope+slug+version): `definition` (JSON of `skillDefinitionSchema`), `sourceEpisodes` (JSON array of real in-scope AgentEpisode IDs, validated at draft time), `testResult` ({passed, steps: [{tool, mocked, ok, detail}]}), `status` (draft|active|retired), `createdBy`/`activatedBy`/`activatedAt`. Definition fields mirror the plan's YAML contract: slug (kebab 3–40), semver version, description, triggers (1–5), allowedTools (subset of TOOL_CONTRACTS, 1–5), steps (1–10 × {tool, input}, each input validated against that tool's proposal schema at draft time — invalid inputs fail draft creation, not runtime), successCriteria.

Lifecycle: propose (ai.use, episodes required) → test (ai.use sandbox: read steps execute for real against scoped data, `set_ai_enabled` steps are mocked to recorded intent with zero side effects) → activate (ai.configure, requires a recorded `passed` evaluation; activating a version retires other active versions of the same slug) → deactivate (ai.configure, status retired). **Rollback** = explicit re-activation of a retired passing version via `rollbackSkill(slug)` (picks latest retired passing version). Skills are data plus governed execution of existing tools; every run through them passes the normal permission/approval/approval-hash/kill-switch path. No skill can grant permissions, alter policy, or activate itself. No auto-generated code steps in this version (declarative tool steps only).

HTTP: `GET/POST /api/admin/agent/skills` (list with optional slug filter / create draft), `GET /api/admin/agent/skills/[id]`, `POST /api/admin/agent/skills/[id]` `{action: test|activate|deactivate}`; rollback via runtime method (UI wiring pending).

## Phase 6 subagent contracts

`AgentRun` gained `parentRunId` (null = supervisor) and `toolCallBudget` (default 12). Spawn: `POST /runs/{id}` `{action:"spawn", subtask:{task 5–300, role, proposal}}`. Roles are fixed read-only tool sets (`SUBAGENT_ROLES`): `data_research` → get_ai_status/search_catalog/list_lessons, `finance` → calculate_sales_report; the proposal must belong to the role **and** be risk=read (`SUBAGENT_WRITE_FORBIDDEN` otherwise) — subagents can never write. Server-enforced limits (`SUBAGENT_LIMITS`): depth 1 (children can never spawn: `SUBAGENT_DEPTH_EXCEEDED`), max 3 concurrent non-terminal children (`SUBAGENT_CONCURRENCY_EXCEEDED`), total children ≤ parent's remaining budget — each spawn deducts one from `toolCallBudget` and the child inherits the remainder (`SUBAGENT_BUDGET_EXCEEDED`). Permissions are re-checked per child tool against the live User role; children are user-scoped and same-scope like any run. Child creation is a normal queued run: it executes only through the governed execute path (identity reloaded, kill switch, receipts).

Supervisor verification: `GET /runs/{id}` returns `children[]` (id, tool, state, parsed result, lastError) so the supervisor (or UI) inspects findings before responding. Cascade cancel: cancelling the parent cancels non-terminal children in the same transaction (already-terminal children keep their receipts); a child mid-transaction finishes atomically and reconciles via its durable receipt. Spawn requires the parent to be non-terminal and not mid-run.

## Phase 7 control panel and release contracts

`GET /api/admin/agent/status`: `{enabled, writes, shadow, canaryActive, approvalQueue, running}` — server-authoritative state for the UI banner (kill-switch indicator; the env flag remains the actual switch). Gradual release is server-side only: `AGENT_SHADOW_MODE=true` blocks write execution with `SHADOW_MODE` (403) while reads and all other flows proceed unchanged; `AGENT_CANARY_USERS` (comma-separated IDs, empty = everyone authorized) is enforced inside `identity()` — unlisted users get `CANARY_NOT_ENROLLED` on every agent call. Client responses never influence these flags; the model cannot observe or set them.

AgentRun schema in `prisma/schema.prisma`: immutable proposal, request hash and scoped unique key; server trace ID; status; captured source version/previous value; approval actor/hash/expiry; durable result; `attemptCount` and `lastError` (column `error`, bounded code only, never raw exception text). Events contain bounded names/state and export marker. Event names: `run.created`, `tool.started`, `tool.verified`, `run.completed`, `run.failed`, `run.attempt_failed`, `control.*`. No parent_run_id/subagent support yet. No generated skill or memory can change these permissions.

## Phase 2 failure and recovery semantics

`AgentError` carries a phase. `policy` phase rejections (e.g. `WRITES_DISABLED`, `STALE_SOURCE`, `APPROVAL_REQUIRED`, `FORBIDDEN`, `INVALID_STATE`) occur before any effect: the run keeps its retryable state, and the attempt is durably recorded (`attemptCount` increment, `lastError` code, `run.attempt_failed` event) in a separate transaction. `execution` phase failures (`VERIFICATION_FAILED`, `UNSAFE_MONEY_VALUE`) are deterministic after the tool started: the transaction rolled back any effect and the run becomes terminal `failed` with a durable `run.failed` event; recovery is a new approved run, never an automatic retry. Unexpected exceptions and transient infrastructure errors (SQLite busy/locked, Prisma P2024) are recorded as `EXECUTION_ERROR` attempts; execute retries them with bounded backoff (3 attempts, 50ms/100ms) — safe because a failed transaction has no effect. A successful execution clears `lastError`. A terminal run replayed via execute or GET returns the stored receipt without re-execution; a lost race in the recorder keeps the original outcome. These are server-enforced invariants; clients cannot set them.

Success answers are formatted by `responseText` directly from verified tool output. Planner only proposes one action through existing text completion and strict JSON validation; unsupported/ambiguous/invalid output fails closed (`PLAN_UNSUPPORTED_OR_UNAVAILABLE`). It does not receive business data or emit the final success/financial response.

## Phase 3 GraphRAG contracts

Models `GraphNode`, `GraphEdge`, `GraphSync` in `prisma/schema.prisma` (migration `003_graph`). Node/edge metadata: `scopeId` (server single-cafe boundary), `sourceId` (`Kind:refId` — joins always by source ID, never name similarity), `sourceVersion` (source updatedAt ISO + content hash), `observedAt`, `validFrom`/`validTo` (validity period), `status` (`active`|`deleted`), `confidence` (direct extraction = 1; model hypotheses would be < 1 and are not produced yet).

Sync (`src/lib/agent/graph/sync.ts`), SQLite interim mapping of the planned pipeline: source `updatedAt` polling replaces the transactional outbox/CDC; `GraphSync.watermark` per entity kind is the consumer cursor; each sync run is also the reconciliation job — deletion propagates by deactivating (not deleting) nodes/edges with `validTo`, stale events never overwrite newer graph versions, and the watermark only advances after a successful pass. Retrieval (`src/lib/agent/graph/retrieval.ts`) filters scope/validity/status before returning anything, is bounded (20 candidates, 40 relation lookups, 1 hop), and stamps results with `graphAsOf` + `stale`; `GRAPH_MAX_STALE_SECONDS` (default 300) gates freshness — a stale graph must never be treated as authoritative for sensitive answers, which are read from the live source.

Stack decision (documented tradeoff): Neo4j/pgvector and a Python LangGraph service are deferred; the interim graph lives in the existing SQLite schema with the same metadata contracts so a later migration can replay `syncGraph` from source. Do not migrate the primary database without explicit authorization.
